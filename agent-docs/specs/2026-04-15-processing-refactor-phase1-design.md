# TinyPic 第一期处理链路重构设计

## 1. 背景

当前仓库已经具备可用功能，但处理链路和界面层耦合较重，主要问题集中在以下几类：

- `core/processor.py` 同时承担输入源识别、图片读取、图像变换、并发调度、结果写出与统计汇总。
- `gui/main_window.py` 同时承担界面布局、线程协调、任务状态管理和设置持久化。
- 图像预处理、宽图处理、JPEG 编码、MozJPEG 优化在多个文件中重复实现，行为有分叉风险。
- 当前处理流程会在任务早期将大量图片字节读入内存，不利于大体积漫画包。
- 自动化测试基本空白，现有行为缺少稳定回归保护。

## 2. 目标

本期目标按优先级排序如下：

1. 提升处理链路的可维护性与可测试性。
2. 降低大任务处理时的内存占用和异常定位成本。
3. 统一单页、双页、旋转、裁剪、灰度、编码的处理实现，减少重复代码。
4. 改进错误回传与进度上报，让 UI 能展示更可靠的处理状态。
5. 在不改变输出格式和命名规则的前提下，允许顺手修正明显行为问题。

## 3. 非目标

以下内容不属于本期范围：

- 不重做完整视觉设计，只做处理链路重构所需的 UI 适配。
- 不改变输出文件格式，输出仍为 `*_tinypic.cbz`。
- 不引入数据库、任务队列服务或新的大型依赖。
- 不主动扩展新的输入格式。

## 4. 方案选择

### 方案 A：渐进式重构

保留 `MainWindow -> WorkerThread -> TaskProcessor` 入口形态，将内部逻辑拆分为更小职责模块，逐步替换现有实现。

优点：

- 回归风险最低。
- 能兼容现有 UI 调用方式。
- 适合在当前仓库直接落地并持续迭代。

缺点：

- 第一阶段后仍会保留少量兼容层。

### 方案 B：重建新 Pipeline

直接重写新的任务模型和处理管线，UI 改为对接新接口。

优点：

- 结构最干净。
- 后续上限最高。

缺点：

- 改动面大，回归风险高。
- 第一阶段周期会明显拉长。

### 方案 C：最小修补

仅提取少量公共函数、补测试并修正局部问题。

优点：

- 成本最低。

缺点：

- 难以真正解决职责混杂问题。
- 后续演进成本依然高。

### 结论

采用方案 A。该方案在风险、收益和实施成本之间最平衡，适合作为第一期改造骨架。

## 5. 目标结构

### 5.1 保留的外部入口

- `gui.main_window.MainWindow`
- `gui` 层工作线程入口
- `core.processor.TaskProcessor`

这些入口继续存在，以降低 UI 和现有调用代码的变动范围。

### 5.2 新的核心职责划分

建议拆分为以下模块：

- `core/sources.py`
  - 负责文件夹、ZIP/CBZ、RAR/CBR、EPUB 的图片枚举与读取。
  - 提供统一的图片项迭代接口，输出顺序稳定。
- `core/models.py`
  - 放置 `ImageTask`、`ImageResult`、`ProcessorStats`、`TaskError` 等数据结构。
  - 明确处理前、中、后各阶段的数据边界。
- `core/encoding.py`
  - 统一 JPEG 编码参数、透明通道处理、MozJPEG 优化。
  - 收敛当前重复的保存与优化逻辑。
- `core/pipeline.py`
  - 负责宽图判断、单页/拆分/旋转决策、裁剪编排、灰度判定、编码调用。
  - 对外暴露“处理一张图片并返回 1 或 2 页结果”的统一接口。
- `core/processor.py`
  - 退化为任务编排器，负责选择输入源、提交并发任务、按顺序写出结果、汇总统计与回调进度。

### 5.3 现有文件的归位策略

- `core/cropper.py` 保留为裁剪算法承载文件。
- `core/compressor.py` 内部公共能力向 `core/encoding.py` 和 `core/pipeline.py` 迁移。
- `core/splitter.py` 中与主流程重复的逻辑被吸收后，视实际使用情况决定保留兼容壳或删除。

## 6. 数据流设计

### 6.1 输入阶段

`TaskProcessor.process(input_path)` 根据输入类型选择图片源。

图片源统一以“有序图片项”的形式输出，每个图片项至少包含：

- 原始序号
- 显示名
- 原始字节读取方法或字节数据
- 是否封面

### 6.2 处理阶段

`pipeline` 对单张图片执行如下步骤：

1. 读取原始图片字节。
2. 判断是否为宽图。
3. 根据 `spread_mode` 选择：
   - `split`
   - `rotate`
   - `none`
4. 对结果页应用裁剪。
5. 做灰度判断与模式规范化。
6. 用统一编码器输出 JPEG。
7. 返回处理结果与统计数据。

### 6.3 写出阶段

`TaskProcessor` 使用有界并发处理图片，但写出阶段保持按原始顺序落入 CBZ，确保页序稳定。

输出命名规则保持不变：

- 文件夹：`<目录名>_tinypic.cbz`
- 压缩包：`<原文件名去后缀>_tinypic.cbz`

## 7. 并发与内存策略

### 7.1 当前问题

现状会提前把大量图片字节装进 `image_data_list`，然后再并发处理，这会放大内存峰值。

### 7.2 本期策略

- 改为“枚举输入项 -> 受控提交任务 -> 收集结果 -> 按序写出”。
- 不要求绝对流式零缓存，但要限制在“仅保留有限数量的待处理项和未写出结果”。
- 并发度仍由 `num_threads` 控制，但实际提交应采用有界窗口，避免一次性把整本书全部提交到线程池。

### 7.3 预期收益

- 大型漫画包的内存占用更可控。
- 取消任务时更容易及时停止后续调度。

## 8. 错误处理与状态上报

### 8.1 错误策略

- 不再大量静默吞异常。
- 输入源解析失败、单页处理失败、写出失败要区分来源。
- 对单张图片失败，默认记录错误并继续任务；对整体输入不可恢复错误，终止当前任务并回传 UI。

### 8.2 UI 可见状态

工作线程至少需要向 UI 回传以下事件信息：

- 当前任务开始
- 当前任务页级进度
- 当前任务完成及统计
- 当前任务失败及错误详情
- 全部任务结束

本期不要求重做界面，但要求 `MainWindow` 能依据这些信号展示更明确的处理状态。

## 9. 设置持久化设计

### 当前问题

滑块值变化会直接触发 `config.json` 写盘，拖动过程中可能造成高频写文件。

### 调整方案

- `Settings` 引入内存态更新与显式 `save/flush`。
- UI 控件在“释放滑块”“切换下拉完成”“窗口关闭”时集中保存。
- 配置键不变，兼容现有 `config.json`。

## 10. 测试设计

本期至少补以下自动化测试：

- 文件夹输入包含子目录时，页序稳定。
- `spread_mode` 为 `split`、`rotate`、`none` 时输出页数与顺序正确。
- 封面页不走双页拆分。
- 裁剪模式 `none`、`margins`、`margins+page` 基本流程可执行。
- 输出文件名规则保持兼容。
- 处理失败时统计与异常回传符合预期。

如样本构造简单可控，优先用 `tests/` 中的小型程序生成图片，而不是依赖大体积真实样本。

## 11. 实施边界与兼容性

### 保持兼容

- `MainWindow` 仍通过工作线程触发处理。
- `TaskProcessor` 名称和对外入口保留。
- 输出格式、文件名后缀、基础配置项保持兼容。

### 允许优化

- 统一原先分散的图像处理逻辑。
- 修正明显的异常吞掉、状态不准确、内存占用偏高等问题。
- 对局部处理策略做更一致的实现，但不以“视觉效果大改”为目标。

## 12. 风险与缓解

### 风险 1：重构后行为回归

缓解：

- 先补测试，再替换实现。
- 保留 `TaskProcessor` 外部接口不变。

### 风险 2：并发重构引入页序错误

缓解：

- 处理结果按输入原始序号回收。
- 写出阶段只按排序后的结果顺序写入。

### 风险 3：来源适配拆分后 RAR/EPUB 行为异常

缓解：

- 为各来源单独设计最小回归用例。
- 保留原路径逻辑作为兼容参考。

## 13. 第一阶段完成标准

满足以下条件可视为第一期完成：

- `core/processor.py` 不再承载大部分图像细节实现。
- 图像编码和宽图处理逻辑只有一套主实现。
- `MainWindow` 中的任务状态管理有所收敛，至少不再直接承担过多底层处理细节。
- 新增核心回归测试并可本地运行。
- 语法检查和测试通过，且手工处理样本能正常输出 `*_tinypic.cbz`。
